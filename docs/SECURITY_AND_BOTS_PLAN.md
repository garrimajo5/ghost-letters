# Безопасность и дальнейшая работа над ботами

План от 9 октября 2026. Рабочая ветка безопасности: `fix/security-hardening`.
Изменения выпускаются через PR; слияние и развёртывание не выполняются автоматически.

## Исправления аудита

- Разделить публичного автора события и закрытого инициатора команды. Для старой истории применять безопасную проекцию, сохранив идемпотентность команд.
- Сериализовать обновление и отзыв refresh-токенов блокировкой аккаунта в PostgreSQL, включая параллельные запросы разных экземпляров API.
- Не выдавать сессию существующего аккаунта по одному deviceId. Сохранить действующие refresh-токены и вход по одноразовому коду. Клиент не обходит отказ сервера повторным гостевым входом, выход отзывает refresh на сервере.
- Закрывать SignalR-соединения по истечении JWT. Ограничить вызовы хаба отдельно от HTTP-запросов.
- Принимать X-Forwarded-For только от явно указанного прокси, один переход. Закрепить адрес Caddy в отдельной сети, не публиковать API наружу.
- Ограничить размер запросов и потоковое чтение файлов, проверить контейнер голосового, добавить квоты пользователя и всего хранилища, ограничить число незакреплённых загрузок, удалять неиспользуемые файлы.
- Обновить уязвимые зависимости и включить аудит транзитивных пакетов при восстановлении.

Проверка: негативные API-тесты, параллельные запросы, доверенный и поддельный прокси, истечение сессии хаба, серверные и клиентские регрессии, Flutter analyze, NuGet audit.

## Особенности выпуска

Клиент и сервер нужно обновлять совместно. Старые клиенты пытались обходить 401 через deviceId; теперь сервер отклоняет этот обход. Существующие сессии продолжают работать. После явного выхода или окончательного истечения сессии для старого аккаунта нужен код с другого авторизованного устройства. Перед выходом клиент объясняет это. Регистрация создаёт новый аккаунт; совпадение ника не подтверждает владение старым.

JWT остаётся действительным до своего срока (обычно 15 минут); выход отзывает refresh, а не уже выпущенный JWT. Проверка контейнера медиа — не полное декодирование, антивирус или проверка заявленной длительности. Загруженные файлы отдаются с `nosniff`.

Квоты по умолчанию: 100 МБ на пользователя, 2 ГБ на хранилище, 5 файлов без ссылки из чата/аватара. Неиспользуемые файлы старше суток удаляются каждые 15 минут, не более 500 за проход. Старые заменённые аватары тоже попадают в очистку. Файлы, закреплённые в чате или профиле, не удаляются. Общая дисковая проверка учитывает и файлы, оставшиеся после сбоя. Квоты настраиваются через `Media:UserQuotaBytes` и `Media:TotalQuotaBytes`; место на диске должно превышать квоту с запасом для БД, журналов и резервных копий. При заполнении квоты загрузки получают 429.

Прокси: `Proxy:KnownProxies` — список IP через запятую. Без него forwarding выключен. В production compose Caddy получает `172.29.214.2`, сеть `172.29.214.0/29`; при конфликте с инфраструктурой эти значения меняются согласованно. Нельзя указывать адреса недоверенных клиентов.

Лимиты в минуту: `RateLimit:AuthPerMinute` 30 по IP, `ReadsPerMinute` 600, `WritesPerMinute` 120, `UploadsPerMinute` 10, `HubCallsPerMinute` 120. Для авторизованных запросов и вызовов хаба лимит общий для пользователя в пределах экземпляра API. При горизонтальном масштабировании перенести счётчики в общий Redis или шлюз. Квоты файлов и блокировки токенов уже общие через PostgreSQL.

## Следующие улучшения безопасности

1. Восстановление аккаунта без второго устройства: телефон с кодом или резервные одноразовые коды. Для SMS отдельно выбрать провайдера, бюджет и правила ограничения попыток.
2. Хранение токенов в системном защищённом хранилище Android/iOS; для веба оценить httpOnly cookies с CSRF-защитой вместо доступного JavaScript хранилища.
3. Семейства сессий, список устройств и немедленный отзыв JWT/соединений; текущий предел после отзыва — срок access-токена.
4. Полное декодирование и нормализация медиа в изолированном процессе с лимитами CPU/памяти; политика хранения голосовых и мониторинг заполнения.
5. Поддерживаемая версия .NET, регулярные обновления образов, централизованные лимиты при нескольких API, резервное копирование с проверкой восстановления.

## Работа над человечностью ботов до 03:00 МСК 10 октября

Создан heartbeat `ghostletters-03-00`: каждый час до `2026-10-10T00:00:00Z`.
Перед каждым проходом проверять время и состояние веток/PR. После срока не начинать новых изменений. Не создавать дублирующих задач, не запускать подагентов, не трогать пользовательскую рабочую копию `D:/AI/GhostLetters`.

Приоритеты небольших проверяемых PR:

1. **Смысл ответа.** Понимать ряд, карту и вопрос из текста без обязательного прикрепления карты; отвечать именно на вопрос, а при неоднозначности уточнять. Не приписывать чужим сообщениям смысл, которого нет.
2. **Связная версия.** Использовать улики всех раундов, различать наблюдение и предположение, объяснять изменение своей версии конкретным аргументом. Не объявлять совпадение цвета доказательством роли.
3. **Диалог.** Избегать одинаковых вступлений и ответов, помнить уже отвеченные вопросы, выбирать адресата с учётом общения и характера. Давать людям время ответить, не устраивать бесконечный обмен ботами.
4. **Характер и симпатия.** Уверенность, упрямство, доверие и симпатия влияют умеренно; подтверждённые игровые факты сильнее личного отношения. Скрытые факторы симпатии не попадают в публичные реплики.
5. **Производительность.** Измерить обращения к БД и время такта; устранить повторные загрузки одних данных в пределах такта, не кэшируя проекции разных ролей вместе. Проверить несколько параллельных партий.

Для каждого прохода: воспроизведение проблемы → ограниченное исправление → тесты/симуляции с фиксированным seed → запись результата и PR. Обязательные инварианты: бот знает только сведения своей роли, не раскрывает скрытые карты и роли, сообщение укладывается в лимиты, одинаковая версия не вызывает спам, ожидание людей не блокирует таймеры.
